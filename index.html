바이브코딩의 기본 원칙

AI가 코드를 작성하더라도 문제 정의, 우선순위, 검증 책임은 개발자에게 있습니다.

작게 시작처음부터 모든 기능을 넣지 않고 핵심 기능 1~3개로 시작합니다.
문서 먼저코드보다 요구사항, 화면, 데이터, 예외 상황을 먼저 기록합니다.
한 단계씩여러 기능을 동시에 요청하지 않고 기능 단위로 구현·검증합니다.
증거로 확인“되는 것 같다”가 아니라 테스트 결과와 오류 로그로 판단합니다.

초보자에게 7단계가 적합할까?

개발 구조로는 적합하지만, 수업에서는 전문 용어보다 사용자가 해야 할 행동을 먼저 제시하는 편이 좋습니다.

검토 결론

7단계는 빠뜨리기 쉬운 기획·검사·배포를 포함한다는 점에서 적절합니다. 다만 입문자는 모든 산출물을 처음부터 완벽히 작성하기보다, 첫 프로젝트에서는 각 단계마다 핵심 질문 1~2개와 결과물 1개만 완성하도록 단순화하는 것이 좋습니다.

확인하고 공유하기6~7단계: 실제처럼 시험하고 다른 사람에게 공개합니다.

쉬운 행동 표현을 먼저 사용하고, 실제 개발 용어는 옆에 함께 표시했습니다.

01

해결할 문제 고르기 아이디어 기획

“무엇을 만들까?”보다 “누구의 어떤 문제를 해결할까?”를 먼저 결정합니다.

핵심 질문

  • 누가 사용하는가?
  • 현재 어떤 불편이 있는가?
  • 결과물이 어떤 행동을 줄이거나 쉽게 만드는가?
  • 성공 여부를 무엇으로 판단할 것인가?

필수 산출물

  • 문제 정의문 1문장
  • 핵심 사용자 1~2명
  • 현재 업무 흐름과 개선 후 흐름
  • 성공 기준 2~3개

교사 업무 예시

  • 연수 대상자가 신청 정보를 스스로 확인·수정하도록 한다.
  • 담당자는 반복 문의와 수기 수정 시간을 줄인다.

자주 발생하는 실수

  • “좋아 보이는 기능”부터 추가함
  • 사용자를 너무 넓게 설정함
  • 문제보다 기술이나 도구를 먼저 선택함
AI 요청 예시나는 [사용자]가 [현재 상황]에서 겪는 [문제]를 해결하는 도구를 만들고 싶다. 사용자가 실제로 수행하는 업무 흐름을 5단계 이내로 정리하고, 가장 큰 불편 3개와 디지털 도구로 개선 가능한 지점을 제안해줘. 아직 기능이나 기술 스택은 결정하지 말고 문제 정의에 집중해줘.
✓ 완료 기준: 사용자, 문제, 기대 변화가 한 문장으로 설명된다.
02

가장 작은 첫 버전 정하기 아이디어 구체화·MVP

사용 장면과 업무 흐름을 시나리오로 바꾸고, MVP 범위를 결정합니다.

핵심 질문

  • 사용자는 처음에 무엇을 보고 시작하는가?
  • 어떤 정보를 입력하고 어떤 결과를 받는가?
  • 반드시 필요한 기능과 나중에 추가할 기능은 무엇인가?
  • 사용 중 실패할 수 있는 상황은 무엇인가?

필수 산출물

  • 대표 사용자 시나리오
  • MVP 기능 목록
  • 제외 기능 목록
  • 화면 흐름도

MVP 판단 기준

  • 문제를 해결하는 최소 기능인가?
  • 없어도 첫 버전을 사용할 수 있는가?
  • 개인정보나 권한 위험이 과도하지 않은가?

자주 발생하는 실수

  • 로그인, 알림, 통계, 관리자 기능을 모두 넣음
  • 예외 상황 없이 정상 흐름만 생각함
  • 사용자가 실제로 누르는 순서를 정의하지 않음
AI 요청 예시아래 문제 정의를 바탕으로 MVP를 설계해줘. [문제 정의 붙여넣기] 1. 대표 사용자 시나리오 2. 반드시 필요한 기능 3. 첫 버전에서 제외할 기능 4. 화면 이동 흐름 5. 실패·예외 상황 을 표로 정리해줘. 기능은 최대 5개로 제한해줘.
✓ 완료 기준: 첫 버전에 넣을 것과 넣지 않을 것이 구분된다.
03

화면과 동작 적기 기능 정의

AI가 추측하지 않도록 기능의 입력, 처리, 출력, 예외, 권한을 명세합니다.

기능 명세의 5요소

  • 입력: 사용자가 넣는 값
  • 처리: 시스템이 수행할 규칙
  • 출력: 화면에 보여줄 결과
  • 예외: 오류·중복·빈값 처리
  • 권한: 누가 조회·수정 가능한가

필수 산출물

  • 기능 명세서
  • 화면 목록과 화면별 구성요소
  • 데이터 항목 및 자료형
  • 검증 규칙과 오류 메시지

데이터 항목 예시

  • 이름: 문자열, 필수, 2~20자
  • 이메일: 문자열, 이메일 형식 검사
  • 신청일시: 날짜·시간, 자동 기록
  • 수정요청: 문자열, 최대 500자

자주 발생하는 실수

  • “적당히”, “깔끔하게”처럼 기준이 없는 표현 사용
  • 데이터 형식과 중복 기준을 생략함
  • 관리자와 일반 사용자 권한을 구분하지 않음
AI 요청 예시다음 MVP 기능을 개발 가능한 기능 명세서로 바꿔줘. [기능 목록 붙여넣기] 각 기능마다 다음 항목을 작성해줘. - 기능명 - 사용자 목적 - 입력값과 검증 규칙 - 처리 절차 - 출력 결과 - 오류·예외 상황 - 사용자 권한 - 완료 조건 모호한 부분은 임의로 결정하지 말고 '결정 필요'로 표시해줘.
✓ 완료 기준: 다른 사람이 명세만 읽고 같은 기능을 구현할 수 있다.
04

눈에 보이는 화면 만들기 프론트엔드 개발

데이터 연결 전에 화면 구조와 사용자 동작을 먼저 확인합니다.

권장 개발 순서

  • 화면 구조와 메뉴
  • 입력창, 버튼, 표 등 UI 요소
  • 반응형 화면
  • 가짜 데이터로 화면 동작 구현
  • 빈 화면·오류·로딩 상태 구현

필수 산출물

  • 화면별 HTML/CSS/JS
  • 사용자 동선 확인 가능한 프로토타입
  • 입력값 기본 검증
  • 로딩·성공·오류 메시지

검토 관점

  • 사용자가 다음 행동을 바로 알 수 있는가?
  • 중요한 버튼이 눈에 띄는가?
  • 모바일에서도 입력하기 쉬운가?
  • 오류가 발생한 이유를 이해할 수 있는가?

자주 발생하는 실수

  • 디자인과 실제 기능 연결을 동시에 요청함
  • 가짜 데이터 없이 바로 서버 연결을 시도함
  • 성공 화면만 만들고 로딩·오류 상태를 빼먹음
AI 요청 예시다음 기능 명세를 바탕으로 프론트엔드 프로토타입을 만들어줘. [기능 명세 붙여넣기] 조건: - 아직 실제 DB나 API에는 연결하지 않는다. - 샘플 데이터로 모든 화면 흐름을 확인할 수 있게 한다. - 로딩, 데이터 없음, 입력 오류, 성공 상태를 각각 구현한다. - 반응형으로 작성한다. - 파일 구조와 각 파일의 역할을 먼저 제시한 뒤 코드를 작성한다.
✓ 완료 기준: 실제 데이터 없이도 사용 흐름 전체를 시연할 수 있다.
05

저장하고 불러오기 연결하기 백엔드·API·DB

저장·조회·수정 규칙과 권한을 구현하고 프론트엔드와 API로 연결합니다.

백엔드 핵심 구성

  • 데이터베이스 또는 스프레드시트
  • 데이터 조회·등록·수정·삭제 기능
  • 입력값 검증
  • 로그인과 권한
  • 오류 기록과 응답

필수 산출물

  • 데이터 구조표
  • API 목록
  • 권한 정책
  • 프론트엔드 연결 코드
  • 오류 처리 규칙

API 예시

  • GET /applications — 신청 목록 조회
  • POST /applications — 신청 등록
  • PATCH /applications/:id — 신청 수정
  • DELETE /applications/:id — 신청 삭제

자주 발생하는 실수

  • 화면에서만 입력값을 검사함
  • 누구나 전체 데이터를 볼 수 있게 함
  • 중복 등록과 동시 수정 상황을 고려하지 않음
  • 비밀번호나 API 키를 코드에 직접 작성함
AI 요청 예시다음 프론트엔드와 기능 명세를 백엔드에 연결하려고 한다. [기능 명세와 현재 파일 구조 붙여넣기] 1. 필요한 데이터 구조 2. API 목록과 요청·응답 형식 3. 서버 측 입력 검증 4. 사용자 권한 5. 오류 처리 6. 환경변수로 분리할 비밀정보 를 먼저 설계해줘. 설계 검토가 끝난 뒤 기능을 한 개씩 구현하고, 매 단계 테스트 방법을 함께 제시해줘.
✓ 완료 기준: 새로고침 후에도 데이터가 유지되고 권한에 따라 기능이 제한된다.
06

실제처럼 여러 상황에서 시험하기 QA

정상 동작뿐 아니라 잘못된 입력, 권한, 중복, 새로고침, 모바일 환경을 검증합니다.

테스트 범주

  • 정상 시나리오
  • 빈값·잘못된 형식
  • 중복 데이터
  • 권한 없는 접근
  • 네트워크 오류
  • 모바일·브라우저 차이

필수 산출물

  • 테스트 케이스

  • 오류 수정 중 다른 기능이 깨졌는지 확인하지 않음
  • 실제 개인정보로 테스트함
AI 요청 예시다음 기능 명세를 기준으로 테스트 케이스를 작성해줘. [기능 명세 붙여넣기] 정상, 경계값, 빈값, 잘못된 형식, 중복, 권한, 네트워크 오류, 모바일 화면, 새로고침 상황을 포함해 표로 작성해줘. 각 항목에 테스트 절차, 입력값, 예상 결과, 실제 결과 기록 칸을 넣어줘.
✓ 완료 기준: 핵심 기능마다 성공·실패 테스트가 있고 모두 결과를 기록했다.

다른 사람이 쓰게 공유하고 관리하기 배포·운영

실제 사용자가 접근할 수 있도록 공개하고, 장애와 변경에 대비합니다.

배포 전 확인

  • 개발용 샘플 데이터 제거
  • API 키와 비밀번호 환경변수 분리
  • 관리자 권한 재확인
  • 개인정보 수집 항목 최소화
  • 백업과 복구 방법 확인

필수 산출물

  • 배포 주소
  • 사용자 안내서
  • 관리자 운영서

  • 서버·DB가 있음: 웹 애플리케이션 호스팅
  • Google Workspace 중심: Apps Script 웹앱
  • 내부 시험용: 로컬 또는 제한된 테스트 환경

자주 발생하는 실수

  • 테스트 주소와 운영 주소를 구분하지 않음
  • 수정 전 백업이나 버전 기록을 남기지 않음
  • 오류가 발생했을 때 이전 버전으로 되돌릴 방법이 없음
AI 요청 예시현재 프로젝트를 실제 사용자에게 배포하려고 한다. [기술 구성과 파일 구조 붙여넣기] 배포 전 점검표를 작성하고, - 비밀정보 관리 - 권한 - 개인정보 - 백업 - 오류 로그 - 롤백 - 사용자 안내 관점에서 위험을 검토해줘. 그다음 이 프로젝트에 적합한 배포 절차를 단계별로 안내해줘.
✓ 완료 기준: 다른 사용자가 배포 주소에서 핵심 기능을 수행하고, 문제 발생 시 복구 절차가 있다.

7단계가 어렵다면: AI와 대화하며 만드는 방법

AI에게 전체 앱을 한 번에 만들어 달라고 하지 않고, 질문을 받으며 한 단계씩 결정하는 방식입니다.

처음에 AI에게 보내는 안내문

아래 문장을 먼저 보내면 AI가 개발을 서두르지 않고 필요한 내용을 차례로 질문하도록 만들 수 있습니다.

AI 동행형 시작 프롬프트나는 웹앱 개발 경험이 거의 없는 교사야. 내가 수업 또는 학교 업무에 사용할 도구를 만들 수 있도록 개발 안내자 역할을 해줘. 규칙: 1. 한 번에 질문은 하나만 해줘. 2. 전문 용어를 사용하면 바로 쉬운 말로 설명해줘. 3. 내가 답하면 지금까지 결정된 내용을 짧게 정리해줘. 4. 화면과 기능이 충분히 정리되기 전에는 코드를 작성하지 마. 5. 첫 버전은 핵심 기능 1~3개만 포함해줘. 6. 코드는 기능 하나씩 만들고, 매번 내가 시험할 방법을 알려줘. 7. 기존에 정상 작동하는 기능을 임의로 삭제하거나 바꾸지 마. 8. 개인정보·로그인·외부 API가 필요하면 위험과 대안을 먼저 설명해줘. 첫 질문은 “누가 어떤 상황에서 사용할 도구인가요?”로 시작해줘.
1

필요한 도구 설명하기

대상을 정하고 현재 불편한 일을 실제 상황처럼 말합니다.

“고등학교 수업에서 학생들이 모둠별 의견을 제출하고, 교사가 한 화면에서 정리해 보는 도구가 필요해.”
다음 단계 조건: 사용자와 해결할 문제가 한 문장으로 정리됨
2

가장 작은 첫 버전 고르기

AI에게 꼭 필요한 기능과 나중에 넣을 기능을 나누게 합니다.

“첫 수업에서 실제로 사용할 수 있는 가장 작은 버전으로 줄여줘. 꼭 필요한 기능은 3개 이하로 제한하고, 나중에 추가할 기능을 따로 적어줘.”
다음 단계 조건: 이번에 만들 기능이 1~3개로 제한됨
3

화면을 글과 그림으로 확인하기

코드 전에 화면 목록과 버튼을 누르는 순서를 검토합니다.

“화면마다 제목, 입력칸, 버튼, 결과 영역을 표로 보여줘. 사용자가 처음 접속한 뒤 완료할 때까지 누르는 순서도 함께 작성해줘.”
다음 단계 조건: 화면 흐름을 읽고 수정할 부분이 없음
4

화면 샘플부터 만들기

아직 저장 기능 없이 가짜 데이터로 화면과 버튼 동작을 확인합니다.

“지금은 서버나 데이터베이스를 연결하지 말고, 하나의 HTML 파일에서 실행되는 화면 샘플을 만들어줘. 가짜 데이터로 모든 버튼을 시험할 수 있게 해줘.”
다음 단계 조건: 화면에서 사용 흐름 전체를 시연할 수 있음
5

저장 기능 하나만 연결하기

저장 위치의 장단점을 들은 뒤 한 가지를 선택합니다.

“이 도구에 적합한 저장 방법을 브라우저 저장, Google Sheets, 일반 데이터베이스로 나눠 쉽게 비교해줘. 내가 선택하면 저장 기능 하나만 연결하고 시험 방법을 알려줘.”
다음 단계 조건: 새로고침 후 데이터 유지 여부를 확인함
6

오류를 찾아 고치고 공유하기

AI에게 테스트 표를 만들게 하고 직접 결과를 기록한 뒤 배포합니다.

“정상 입력, 빈칸, 잘못된 입력, 중복 제출, 모바일 화면을 시험하는 표를 만들어줘. 오류를 전달하면 원인을 추측하기 전에 재현 절차와 오류 메시지를 먼저 확인해줘.”
완료 조건: 핵심 테스트 통과, 배포 주소와 복구 방법 확보

수업용 웹앱 개발에 유용한 JavaScript 라이브러리

라이브러리는 특정 기능을 이미 만들어 둔 코드 묶음입니다. 목적에 맞는 것만 최소한으로 선택해야 합니다.

먼저 확인: 단순 퀴즈, 계산기, 입력 폼, 타이머는 HTML·CSS·JavaScript만으로 충분할 수 있습니다. 라이브러리를 추가하면 기능은 빨리 만들 수 있지만 파일 크기, 학습 난이도, 오류 원인도 함께 늘어납니다.
표·그래프처음에는 Chart.js, 매우 자유로운 시각화는 D3
움직이는 수업 자료간단한 상호작용은 p5.js, 3D는 three.js
게임·시뮬레이션물리 현상은 Matter.js, 2D 게임은 Phaser
AI 체험입문 수업은 ml5.js, 세밀한 모델 제어는 TensorFlow.js

아래 내용을 채운 뒤 AI에게 전달하면 코드 생성 전에 요구사항을 정리할 수 있습니다.

학교 현장에서 특히 주의할 사항

학생·학부모·교직원의 개인정보를 실제 개발·테스트 데이터로 사용하지 마세요. 최소 수집, 접근 권한, 보관 기간, 삭제 방법을 먼저 정하고, 외부 AI 서비스에 민감한 정보를 그대로 입력하지 않아야 합니다.

AI에게 맡길 일과 사람이 결정할 일

AI는 아이디어 확장, 코드 초안, 테스트 목록, 오류 원인 후보를 제시하는 데 유용합니다. 그러나 문제 정의, 개인정보 처리, 권한 정책, 최종 검증, 배포 책임은 사람이 결정해야 합니다.

좋은 바이브코딩은 좋은 개발 프로세스에서 시작됩니다.
